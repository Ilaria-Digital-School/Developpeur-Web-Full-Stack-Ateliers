# Écrire le Product Backlog du projet en user stories

Rappel théorique et mise en contexte Le Product Backlog est l'artefact central en Scrum. Il s'agit de la liste priorisée et évolutive de tout ce qui est nécessaire pour réaliser le produit. Chaque élément de cette liste décrit une fonctionnalité, une amélioration ou une correction. En méthode agile, la forme privilégiée pour exprimer ces besoins est la user story. Une user story est une description simple et concise d'une fonctionnalité, rédigée du point de vue de l'utilisateur final ou d'un autre rôle concerné. Son objectif est de capturer un besoin métier concret sans entrer prématurément dans les détails techniques. Le format classique est : "En tant que [rôle], je veux [fonctionnalité] afin de [bénéfice ou valeur]." Ce format oblige à identifier clairement l'acteur, l'action et la justification. Un modèle mental essentiel est de considérer les user stories comme des promesses de conversation. Ce n'est pas un document contractuel figé, mais un support pour un dialogue approfondi entre l'équipe de développement et le Product Owner. La granularité est une notion clé : une story doit être suffisamment petite pour être développée, testée et potentiellement livrée au cours d'un sprint unique. Les erreurs fréquentes sont nombreuses. On observe souvent des stories trop vastes, appelées épopées, qui ne peuvent pas être traitées en un sprint. À l'inverse, des stories trop techniques oublient le point de vue utilisateur.
